# 📦 Building AuthCore for every version (1.16.x – 26.x)

Minecraft changed the rules at **26.1**: Mojang released the game **unobfuscated** (readable
Mojang names in the shipped jar, parameter names included) and **Fabric's intermediary no
longer exists** for that era. The Fabric project [announced](https://fabricmc.net/2025/10/31/obfuscation.html)
that yarn is discontinued and mods must migrate to Mojang names.

That is why AuthCore ships **two jars**:

| Jar | Source tree | Names | Minecraft | Java level |
|:----|:------------|:------|:----------|:-----------|
| `authcore-classic-<v>.jar` | `src/classic/java` + `src/client/java` | Yarn | 1.16.0 – 1.21.11 | 16 |
| `authcore-modern-<v>.jar` | `src/modern/java` | Mojang | 26.0+ | 25 |

The two name-spaces **cannot coexist in one compiled jar** — the game at runtime uses either
intermediary (≤1.21.11) or Mojang names (≥26.1). Installing the right jar per server version
is expected behaviour for every mod today.

> 🧩 **Bonus: each jar also acts as a BungeeCord / Velocity plugin** (`bungee.yml` +
> `velocity-plugin.json` + `net.ded3ec.proxy.*`). The proxy role is version-independent, so it
> is compiled ONCE in `src/common/java` and lands in **both** jars — drop either jar into a
> proxy's `plugins/` folder and it auto-detects (config: `config/authcore-proxy.properties`).

## Source layout

```
src/
├── common/java/       SHARED code - pure Java, no Minecraft imports, used by BOTH jars
│                      (database, config, password hashing, web panel, redis, security
│                       logic, task scheduling, proxy plugin, ...). Edit once, both builds get it.
├── classic/java/      classic yarn-named server code (1.16 – 1.21.11)
├── client/java/       classic yarn-named client companion
├── modern/java/       Mojang-named code for 26.0+ (server + client companion)
├── common/resources/  bungee.yml + velocity-plugin.json (proxy plugin manifests - both jars)
├── classic/resources/ classic fabric.mod.json + mixin configs + assets (shared)
└── modern/resources/  26.x fabric.mod.json (mixins/assets shared from src/classic/resources)
```

## Building

```bash
# Classic universal jar (1.16 – 1.21.11) - needs a Java 21+ JDK
./gradlew clean build                                   # -> build/libs/authcore-classic-1.0.0.jar

# 26.x jar (26.0+) - needs a Java 25 JDK
./gradlew clean build -Pmodern=true \
  -Pfabric.loom.disableObfuscation=true                 # -> build/libs/authcore-modern-1.0.0.jar

# Per-version verification jars (used by the CI matrix; not meant for release)
./gradlew clean build -Puniversal=false
```

Both commands share ONE build script, ONE wrapper and ONE loom version (1.16.x).
CI builds and verifies both jars on every push (`.github/workflows/ci.yml`) and attaches both
to the GitHub Release on `v*` tags.

## Keeping the two sources in sync

`src/modern/java` is the yarn source **migrated to Mojang names** (loom's `migrateMappings`
task, see [Fabric docs](https://docs.fabricmc.net/develop/porting/mappings/loom)).
When you change business logic, port the change to both trees (mechanical renames stay
identical; 26.x-only API differences are small).

### Migrating a change (or re-syncing) with loom

```bash
# From a clean copy of the repo with loom 1.16.x and yarn 1.21.11 configured:
./gradlew migrateMappings \
  --mappings "net.minecraft:mappings:1.21.11" \
  --overrideInputsIHaveABackup
#    (default input: src/main/java - migrate server code)
# 2. Then apply the 26.2-specific manual fixes (mixin targets, renamed APIs)
#    as documented below; commit the result to src/modern/java.
```

> ⚠️ Back up first: `--overrideInputsIHaveABackup` rewrites in place.

### 26.x API differences already handled in `src/modern/java`

- `net.minecraft.block.*` imports → `net.minecraft.world.level.block.*` (wildcard imports are
  NOT rewritten by migrateMappings)
- `displayClientMessage(Component, boolean)` → `sendSystemMessage(Component, boolean)`
- `ClickType` → `ContainerInput` (same constants)
- `MinecraftClient` → `Minecraft`; `ClientPlayNetworkHandler` → `ClientPacketListener`
- Screen model: `render(GuiGraphics)` → `extractRenderState(GuiGraphicsExtractor)` +
  `extractBackground(...)`; `setScreen` → `setScreenAndShow`; `drawCenteredString` →
  `graphics.centeredText(...)`
- Reflection string class names updated to Mojang paths (e.g.
  `net.minecraft.client.multiplayer.TransferState`)

### How to find 26.2 API ground truth

The 26.2 game jar is unobfuscated, so `javap` gives exact answers:

```bash
javap -cp ~/.gradle/caches/fabric-loom/26.2/minecraft-merged.jar \
  net.minecraft.client.gui.screens.Screen
```

## 🔍 26.x snapshot verification

The CI runs a **daily snapshot job** (`ci.yml` -> `snapshots`): it queries the Fabric maven
for the newest `26.x` yarn build and, when it differs from the pinned `26.2`, compiles the
modern source against it (`-Pmodern=true`). The job **fails visibly** if the new release
breaks the build - so support lands the moment Fabric publishes mappings, not weeks later.
Run it manually anytime via Actions -> CI -> workflow_dispatch.
