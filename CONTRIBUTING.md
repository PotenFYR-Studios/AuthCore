# Contributing to AuthCore

Thanks for helping improve AuthCore! This guide covers what you need to know to report issues, improve the docs, or ship code across the six Stonecutter build variants.

## Reporting issues

- **Bugs**: open a GitHub Issue using the **Bug Report** form (it asks for your AuthCore version, loader, Minecraft/Java versions, and reproduction steps). Search existing issues first.
- **Features**: open a GitHub Issue using the **Feature Request** form and describe the problem you are solving, not just the solution.
- **Documentation**: use the **Documentation** form for typos, unclear passages, or missing pages at [authcore.docs.potenfyr.in](https://authcore.docs.potenfyr.in).
- **Questions**: the **Question** form or the community Discord works best.
- **Security vulnerabilities**: **never** in public issues - see [SECURITY.md](SECURITY.md) for the private reporting channels.

## Development setup

AuthCore is a **Gradle + Stonecutter (Stonecraft)** multi-loader workspace: one source tree in `src/main/java` (Mojang mappings) compiled per *version group × loader* into six release jars.

Prerequisites:

- **Any installed JDK** (17+) to launch Gradle - the toolchains auto-provision **JDK 17 / 21 / 25** for the build groups (G1: 1.16-1.18 → 17, G2: 1.19-1.21 → 21, G3: 26.1-26.2 → 25). The first build downloads toolchains automatically.
- Optional: `bash test/install-java-and-provided-jars.sh` installs portable Adoptium JDKs and the vendored proxy/API jars under `java-jars/` (the test scripts run it automatically if missing).
- **Bun** only if you work on the documentation app in `docs/app`.

Workspace notes (matches `.gitignore`):

- `versions/<mc>-<loader>/` variant projects are **generated by Stonecutter** - only `versions/dependencies/*.properties` is tracked. Gradle regenerates variants on first run after cloning.
- `dist/` (built jars) and `java-jars/` are local, never committed.
- The active variant for bare `./gradlew` invocations is recorded in `stonecutter.gradle.kts` (auto-managed - do not edit it; use per-variant paths or `buildAll`).

## Build, test, and verify

```bash
# Build ALL six release variants and stage them into dist/
./gradlew buildAll

# Build only one variant
./gradlew :1.21.11-fabric:build        # active variant
./gradlew :1.18.2-forge:build          # any variant project

# Build everything + run the standalone security/migration test suite (~180 checks)
./gradlew testAll

# Run the security suite alone against a built variant
bash test/run-security-tests.sh 1.21.11-fabric

# Docker host tests: boot real servers (requires Docker)
./gradlew dockerTest                         # smoke set
bash test/docker/run-tests.sh --all          # full range-endpoint matrix
bash test/docker/run-tests.sh --groups 1.19-1.21 --java 21 --smoke
```

Documentation app:

```bash
cd docs/app
bun install --frozen-lockfile
bun run build        # outputs docs/app/dist (do not commit)
```

There is no separate formatting/lint gate in CI - format Java consistently with the existing sources (google-java-format conventions: 2-space indent, 100-column lines) before opening a PR.

## Branches and pull requests

- Branch from `master` with a descriptive name (`fix/limbo-velocity-hmac`, `feature/email-otp-rate-limit`).
- Keep changes portable across loaders: put shared logic in `src/main/java`, thin entrypoints in `src/fabric/java`, `src/forge/java`, `src/neoforge/java`, and use Stonecutter conditional comments for version differences (see `settings.gradle.kts` header).
- CI builds all six variants in parallel, runs the security suite, verifies jar roles, and boots Docker host tests - a green CI is the merge bar.
- A PR that changes runtime behavior should state which variants/build groups you verified locally.

### PR expectations

1. One logical change per PR (refactors separate from fixes).
2. All CI checks green (build matrix, security tests, host tests).
3. Player-facing behavior or config changes come with matching updates in `docs/app/content/*.html` and, if needed, the bundled `messages-*.conf` locale keys.
4. Follow the PR template so reviewers can reproduce your testing.

## Documentation contributions

The docs site is generated from `docs/app/content/*.html` (per-page meta in each file feeds titles/descriptions/canonicals) plus the React shell in `docs/app/src/`. Versioned pages live under `/docs/1.0.0/` on deploy. If you add or rename a page, also update the root `sitemap.xml` and `llms.txt`.
